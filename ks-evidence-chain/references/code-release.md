# 代码与数据披露包

投稿包 `05_代码与数据/` 的内容规范。读者是审稿人和复现者，他们用包里的文件复算正文的关键数字。

## 披露范围按"能不能重算"决定，不按方法新不新

没有提出新方法也需要披露，审稿人要的是重算材料。最小披露是能独立重算正文关键数字的最小集合，通常包括：

- 输入表：样本的层归属、层总体数、最终标签、权重，去标识后
- 配置：参数、阈值、随机种子、情景设定
- 脚本：从输入表到正文数字的那几个，含汇总与出表
- 结果表：正文与补充材料引用的那些
- 说明：一条命令跑完，加一张期望输出核对表

确有新方法时另加实现与一个能跑通的最小示例。数据受限时给去标识版或合成版，并写清哪些数字因此不能完全复现。

**只补不加**：包里的脚本就是项目现役脚本，不为投稿另写一套"干净版"。另写的版本未经验证，复现者算出不同的数时会质疑结果本身。

### 从关键数字反推入包文件

从数字往回找，不从 `代码/` 目录往外筛：

1. 列出正文与补充材料引用的数字、图、表，即 README 期望输出核对表的完整版。
2. 为每一项找到直接产出它的脚本和它读入的文件（运行元数据里有记录）。
3. 顺着这些脚本的本地 import、它们读入的上游结果、上游结果的产出脚本继续追，直到原始输入。
4. 追到的文件是依赖闭包。代码与数据只取闭包，README、许可证照常入包。探索脚本、调参与敏感性试跑、废弃版本、画草图的 notebook、一次性检查脚本都不进包。
5. 闭包按文件取，不在包里的副本上裁剪函数，否则包里的就不再是现役代码。公共模块里与本文无关的部分多到妨碍阅读时，在现役代码里拆成独立模块，重跑确认结果不变，再重新取闭包。

补充材料里报告的敏感性分析和稳健性检验属于"被引用的结果"，它们的脚本在闭包内；只在项目内部看过、稿件没报告的试跑不在。

## 自足性

包内路径闭合：不读包外文件，不写包外目录。在干净目录解压后按 README 跑一遍，这是最直接的验证，比逐条对清单可靠。

## README 写什么

环境（语言版本、关键依赖版本）、一条运行命令、输入与输出的对应、预计耗时、期望输出核对表（三到五个正文关键数字，注明所在文件与列名）。不写项目历史、改动史、致谢。

## 路径与隐私卫生

打包前扫一遍，脚本、配置、CSV、Markdown、notebook 输出全扫：

- 本机绝对路径（`C:\Users\...`、`D:\`、`/home/...`、OneDrive 路径）、用户名、机器名
- 内网地址、账号、密钥、token
- 保密坐标、判读人与被调查对象真名、个人联系方式
- 内部文件名与目录名（`历史版本/`、`superseded_`、`.dispatch/`、审查底稿）
- notebook 未清理的执行计数与输出里的路径

脚本里的路径改成相对路径或命令行参数，默认值指向包内。CSV 里若有来源路径列，改成文件名或删掉该列。

## 代码风格

迭代期就按本节写，打包时只做核对。迭代期唯一的例外是第二节第 7 条要求的脚本头部取代说明，它服务于项目内溯源，入包时只留其中的口径，"取代了谁"删去。打包时改动了结构，必须按"自足性"重跑并对上期望输出核对表。

### 注释：最小，且只写口径

能从代码直接读出来的，不写注释。只写一类注释，即**口径**：分母是哪个集合、聚合是合并池还是分组平均、报的是极值还是均值、相关的是哪两列、单位与变换、随机种子的作用范围。这与迭代期第 5 条是同一要求；投稿包里只保留这类注释。

删掉：

- 复述代码的逐行注释（`pd.read_csv` 上面写 `# 读取数据`）
- 改动史与版本说明（`# 原来用 A，现在改成 B`、`# v2 修复`）
- 过程与思考痕迹：TODO、FIXME、"这里可能有问题"、被注释掉的旧代码块
- 分隔线、装饰性区块标题，以及给每个函数套的模板化 docstring
- 指向内部材料的注释：companion paper、审稿轮次、内部报告编号、内部路径
- 教程腔（`# Here we ...`、`# Now we ...`）和注释里的 Markdown 列表、加粗、标题

函数确实需要说明时写一两句，说清它算的是什么量、输入输出是什么；除非项目本来就用三段式 docstring，否则不套 Args/Returns/Raises 模板。

### 结构：写成研究脚本，不写成产品

分析脚本的读者要顺着读下去、对上公式。AI 生成的代码常带以下冗余，写时不加，见到就删：

- 防御性包裹：每个函数都 `try/except` 后打印一句再继续；对不会出现的输入做类型与范围校验；吞掉异常后返回默认值。研究脚本出错就该直接报错停下，悄悄继续会产出错的数。只在确有已知失败情形的地方处理，并写明原因。
- 输出噪声：分隔线横幅、emoji、`✓ Done!`、逐步进度播报、把参数再打印一遍。保留能核对结果的输出，如样本量、关键中间值、写出的文件名。
- 过度参数化：只用一次的值做成命令行参数、配置文件或全局常量表；为未来扩展预留的开关与分支。需要改的参数（输出目录、种子、情景）才做成参数。
- 过度封装：一两行逻辑单独成函数、只有一个方法的类、只转发调用的包装层、为单一实现建的抽象基类。
- 重复实现：同一计算在几个脚本里各写一遍，或 `xxx`、`xxx_v2`、`xxx_final` 并存（按第二节第 7 条归档）。
- 命名：`processed_filtered_normalized_data_df` 这类把处理史写进名字的变量；单位与量写进名字即可（`no3_mgL`、`depth_m`）。
- 兜底与回退：找不到文件就换一个路径试、算不出就用近似值代替，这些都应当报错。
- 状态包装返回：`{"status": "success", "data": ...}` 这类返回值。分析函数直接返回结果，出错就抛异常。
- 附带的演示：文件末尾的 `Example usage`、演示用 `__main__` 块、示例数据生成。脚本真正的运行入口保留。
- 没用到的 import 与依赖；README 和环境文件只列实际用到的包。

判断标准：删掉一行后，结果、报错行为和可读性都不变，这一行就不该在。删掉吞异常的包裹、兜底或回退会改变出错时的行为（从悄悄返回默认值变成报错），这通常是对的，但要逐条列进改动说明，不混在风格清理里。

另一类不属于风格清理：调用了所装版本里不存在的函数或参数。不删，先标出来，按所装版本的文档核实后再改，不凭印象补写。

## 打包前自查

- 干净目录跑通，输出与期望核对表一致
- 包内每个脚本都在关键数字的依赖闭包里，无探索、试跑、废弃版本
- 注释与结构按"代码风格"核对过
- 路径与隐私扫描无命中（可脚本化 grep）
- 包内脚本与现役脚本同源
- README 里的命令和实际文件名对得上
- 可用性声明的措辞与包内内容一致
