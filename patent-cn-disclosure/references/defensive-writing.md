# 防御性写作与可读性（成文时遵守＋审查时执行）

交底书的防御性写作问题有**两个相反方向**，都要管：

1. **读不懂**：为精简而自造黑话、文言式凝练、简单逻辑谜语化——代理人读不懂就写不出现代理质量的申请文件。
2. **处处设防**：预答想象中的审查意见、堆叠免责与括号解释、处处完美主义——反而遮挡技术方案本身。

## 1. 写作规则（成文时遵守，self-check §6 机械复核）

### 1.1 可读性硬规则
- **括号密度**：任一段落中括号内容占比 ≤ 1/3；**禁止括号嵌套**（括号里又有括号）。补充信息优先拆成独立句。
- **破折号禁连用**：不得出现 3 个及以上连续"—"字符（含两个破折号"————"连用；标准双字符"——"单独使用不在此限）；解释性插入语改用逗号或独立句。
- **禁生僻自创词**：凡领域内无通用叫法的自造词（状态代号绰号、机制简称、"××式××"）一律改为直白说法；命名用领域通用词或日常词。
- **不刻意凝练**：禁止四字断句式压缩（"距离升序次之，行列升序兜底"这类）；把输入、判断条件、输出说全，主谓宾齐。通俗好懂的表达一律保留，**"口语化"不是缺陷**。
- **简单逻辑直说**：能用"先看A，相同则看B，最后按C去重"说清的，不用抽象名词或复杂字典序包装。
- **标题少用括号**；正文用词统一（"公知"→"通用手段/常用手段"）。
- **难懂编码表述展开**：如紧凑的编号规则写法要展开成完整句子说明。
- **用词替换表（开放清单）**：下表禁用词全文 grep 应为 0 命中；案件中再遇同类黑话随案增补进问题清单并沿用同一替换：

  | 禁用词 | 替换为 |
  |---|---|
  | 同族 | 直接说明（如"同一发明在其他国家/地区申请的专利"）或删去不提 |
  | 显式留痕 | 写明"做了什么＋记录在案"（如"结果写入备注列"） |
  | 消费（数据/产物/输入） | 使用、需要 |
  | 业务 | 按语境换"人工给定/使用者给定/应用"等，全篇避开"业务"二字 |

- **单位规范**：距离默认用 km（整数或一位小数），小于 1 km 才用 m；其他物理量同理选日常单位并全文统一。

### 1.2 术语处理：改名 vs 定义（二选一，不混用）

**默认全局改名**（交底书阶段措辞最终由代理人重定，直白优先）。同时满足三条即改：
1. 该词是纯包装、不承载独立技术信息；
2. 有同样短或更短的直白说法/标准术语；
3. 替换后全篇语义不变、不产生新歧义。

**例外保留＋首次定义**（满足任一条考虑保留）：
1. 是某机制/判据的名称，后文多次当操作对象引用，直白替换会让句子冗长到影响可读性；
2. 已进入权利要求草稿或附图标注，形成引用链，改名须三处同步、代价大于收益；
3. 直白替换会与其他概念撞名。

定义格式：首次出现处写"〈人话全称〉（下称"XX"）"，全文统一；**禁止"既保留黑话又不定义"**。混合情形：机制名保留定义，其周围的描述性黑话全部直白化。
**执行纪律**：改名零残留（grep 旧词断言 0 命中）；替换词与权利要求草稿、附图叫法一致。

### 1.3 过度防御（D1–D10 审计，中文化转译自 ks-paper-polish defensive-writing.md，原分类参考 Worigin0314/academic-defensive-writing-auditor MIT）

| 类 | 名称 | 中文信号句（示例） | 处理 |
|---|---|---|---|
| D1 | 预答审查员 | "需要注意的是／应当指出／特别说明／为避免误解" | 直接陈述技术事实，删提醒语 |
| D2 | 反复声明不主张 | "并不意图／不应被解释为／不构成对保护范围的限制／仅为示例性说明，不构成限制" | 直接陈述有支持的主张；合并重复边界；保留有独立含义的否定 |
| D3 | 限定堆叠 | 一句内"可能／一定程度上／仅当／大约／在一些情况下"多个叠加 | 去掉重复弱化，保留各自改变推断的条件 |
| D4 | 为弱结果开脱 | "由于规模有限，该效果已属良好／考虑到系统复杂性，这是合理的" | 先报结果；有证据才解释 |
| D5 | 为缺失工作辩护 | "受数据可获得性限制未能…／有待进一步研究"（多处） | 真实缺失在限定处写一次；其余只描述做了什么 |
| D6 | 把控制说成公平 | "为公平比较／为保证可比性／可以认为这足以说明" | 直接写控制了什么变量 |
| D7 | 反复标注初步性 | "初步／示例性／示意性"多处出现 | 只在技术必要处使用 |
| D8 | 褒义词补偿证据 | "显著／鲁棒／全面／高效／明显优于"无对应数据 | 换成已有测量值或具名事实；**同时反查过度声称** |
| D9 | AI式总结句 | "综上所述，上述各方面共同表明／为…奠定了坚实基础" | 冗余则删；否则改成数据支持的那一条推断 |
| D10 | 绝对化辩护 | "不可能／没有任何方法能够／完全排除／无需赘述" | 写出支持该说法的具体条件 |

**必要性判定五问**（每命中句）：①删掉它，读者会被误导吗？②它报告的是有证据的条件/限制吗？③它主要在回答想象中的批评吗？④能改写成"评估了什么、观察到什么、什么在范围外"的正面陈述吗？⑤同一限定前面出现过吗？→ 判：必要限定（保留）/ 纯辩护（删或改）/ 混合（去辩护措辞留事实）。
**原则**：限定只完整解释一次；事实先行；不增加技术信息的句子优先删；"直接删除就好，不要处处要完美"。删除"（全文已通读）"式自证表述。

## 2. 防御性表达审查（workflow Step 6.5，默认必做）

多模型共识分流：**多路独立审查、取交集分级**——多个模型都读不懂的地方是高置信命中，单模型命中的降权处理；人工核对先看交集。

### 2.1 审查提示词（两版，〈占位〉按案件填写）

**框架版**（派给同厂商两路）——核心要素：
```text
请帮我审阅以下专利技术交底书全文。
【背景说明】这是〈案件领域〉领域的发明专利技术交底书，预期读者是专利代理人。文中"〈本案标准术语列举，如：专业算法名、数据结构名、领域基础名词〉"等标准领域术语属于正常技术用语，不算问题，不要标记。通俗好懂的表达一律保留。
【审查目标】只排查一类问题：完全读不懂、造成阅读障碍的重度防御性表达——为字数精简而自造黑话、包装概念、省略主谓宾和技术因果，导致第一次接触本文档的读者无法还原"这句话到底在做什么处理或判断"。读得懂但啰嗦的不要报。
【三类问题】1 生造黑话/借壳造词；2 过度文言式凝练/省略逻辑（缺主谓宾、缺技术因果）；3 简单逻辑包装成抽象谜语。
【硬性要求】"人话表达"一栏只准用原文已有信息还原；信息不足时一律写"无法确定，需作者澄清：缺××信息"，严禁凭常识补全技术逻辑。同一词多处出现合并为一行并列出其他出现位置。
【输出格式】表一：阅读障碍命中表（序号｜章节｜原句｜其他出现位置｜类别1/2/3｜为什么读不懂｜人话表达或"无法确定"）；表二：生造概念人话直译对照表（自造词｜人话说法｜原文判断依据）。最后清点命中数与"无法确定"数。
【交底书全文如下】（粘贴全文）
```

**盲验中性版**（派给第三路高档模型，**不给分类、不给任何示例词**，防提示词框架传染）：
```text
以下是一篇专利技术交底书全文。请以第一次接触这份文档的读者身份独立通读，找出所有你读不懂、或无法确切还原其技术含义的表述：包括看不懂的自造词、压缩到看不清技术因果的句子、绕得让人猜不出真实操作的表述。对每一处：引用原文，说明为什么读不懂（缺了什么信息、可能误解成什么），并给出仅凭原文信息能还原的通俗说法；不够还原的明确写"仅凭原文无法还原，需要作者澄清"。只报读不懂的，不报啰嗦或风格问题。不要猜测提供者想听什么。每条必含：原文、原因、通俗说法（或"无法还原"）。
【全文如下】（粘贴全文）
```

### 2.2 派发手册（经 ai-cross，3 路 2 厂商；通道档位按 ai-cross manifest 当时有效值）

| 路 | 通道/档位 | 思考 | 任务文件 | 定位 |
|---|---|---|---|---|
| 1 | 厂商A 低档 | 关 | 框架版 | 地毯扫描 |
| 2 | 厂商B 中档 | 关 | 框架版 | 跨厂商复核 |
| 3 | 厂商B 高档 | 开 | 盲验版 | 跨节一致性＋框架外盲区 |

命令骨架（Git Bash，**前台运行**；具体通道名以本机 `C:\Users\Akesu\.zcode\skills\ai-cross\` manifest 为准）：
```bash
export PATH="$HOME/.local/bin:$PATH"; export PYTHONIOENCODING=utf-8 PYTHONUTF8=1
cd "C:/Users/Akesu/.zcode/skills/ai-cross"
python references/cc_switch.py exec --provider "〈通道〉" --tier "〈档位〉" \
  --task-file "〈案件文件夹〉/dispatch/task-framed.txt" --tools "" --usage --timeout 400
```

**环境要点（实测坑）**：任务走 `--task-file`（`--task` 经 argv 在换行处截断）；纯文本审查 `--tools ""` 只读最省且免宿主技能污染；必须 UTF-8 环境变量（GBK 吞特殊字符）；高档深思考 200–400s，超时先升 400 再熔断；**禁后台 shell** 派发（实测故障）；某路连续失败 2 次→熔断换备选档或降级 2 路继续，留痕记录。
**留痕**：`dispatch/<时间戳>-<通道>-<档位>.md`（通道、模型、任务文件路径、原始输出、token、耗时）＋两份任务文件 task-framed.txt / task-blind.txt。

### 2.3 合并规则（编排者执行）

1. **不采信模型自算计数**（实测模型计数仅 3/8 正确）——词频与出现位置由编排者 grep 机械统计作权威列。
2. 去重对齐（同一处不同措辞归并）→ 置信分级：**高置信**＝≥2 路独立命中（跨厂商共识，人工优先看）；**低置信**＝单路命中（快速过，可能误报或独有盲区）；分类分歧并列交裁决。
3. 模型标"无法确定"的进**待澄清清单**；编排者不得替模型补写其没给出的技术还原。

### 2.4 人工核对三问（用户执行，skill 只准备材料）

①"读不懂"判定对不对（正常术语被当黑话→划掉）？②"人话表达"技术上对不对（对照实际逻辑核实）？③待改词适用"改名"还是"定义"（§1.2）？替换词与权利要求草稿、附图叫法一致吗？

### 2.5 修改与回检验收（agent 执行修改）

- **授权边界**：本轮修改只限"翻译/还原"，不得补技术内容；"待澄清"处禁止自行编造技术机制填充，交用户决定。
- 修改后回检四项：①同一框架版提示词复审，原命中清零或降为可读；②改名旧词 grep 零残留；③关键数字保真（〈案件关键数字清单〉逐个断言，来自技术要素梳理）；④闭环重扫防修改中新引入黑话。
- 红字注意事项（docx-format §红字两阶段）在用户确认后才删；回检通过＋红字清零＝定稿前提。
