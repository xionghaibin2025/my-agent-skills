# Word 格式底层模板与生成管线（Step 8 必读）

## 1. 格式优先级

1. 案件 `3_参考交底书/` 或代理机构模板**有明确格式要求** → 仿该格式，差异点记录进问题清单；
2. 否则 → **一律用本 skill 底层模板** `scripts/docx生成/generate.js`（规格见 §2，参数经真实案件九轮修订用户确认）；
3. **禁止**无 reference-doc 的裸 pandoc、禁止"会话自行发挥"的生成方式。

## 2. 底层模板格式规格（generate.js 内置常量，勿随意改动）

| 项 | 值 |
|---|---|
| 页面 | A4（11906×16838 twips）；页边距 上/右/下 2.5cm（1417）、左 3.0cm（1701）；页眉/页脚 1.25cm（708） |
| 正文 | 中文宋体（SimSun）＋西文 Calibri，12pt（sz24），1.3 倍行距（line 312 auto），首行缩进 2 字符（420 twips），两端对齐 |
| 文档标题 | 黑体（SimHei）22pt（sz44）加粗居中 |
| 一级标题（##） | 黑体 16pt（sz32）加粗 |
| 二级标题（###） | 黑体 14pt（sz28）加粗 |
| 三级标题（####） | 黑体 12pt（sz24）加粗 |
| 表格 | 100% 宽；表头黑体加粗 10.5pt（sz21）＋浅灰底（F1F5F9）；表体宋体 10.5pt；灰蓝细边框；跨页不断行 |
| 图与图题 | 图居中；图题＝黑体加粗 10.5pt 色 404040 居中，独立段落（"图N　图题"全角空格分隔）；**图注加粗是毕业论文与专利的通用要求** |
| 公式 | 一律 OMML 原生公式（LaTeX→OMML，`$$…$$` 显示式、`$…$` 行内）；**禁止公式截图/图片**；显示公式居中＋编号"（N）"右对齐（tab stop 实现），编号按出现顺序 |
| 页眉 | 居中 9pt 灰（888888）："技术交底书——〈案件名称〉"（自动取 md 案件名称行） |
| 页脚 | 居中页码（9pt） |
| 红字 | C00000（见 §4 红字两阶段）；红字用黑体（与正文宋体区分） |
| 引用块（>） | 楷体 11pt 灰（595959），左缩进 |
| 标题防孤行（v5.1） | 二级/三级/四级标题段自动带 keepNext（标题不孤悬页底；此前案件曾需 python-docx 后处理补此属性，现已内置） |
| 公式符号（v5.1） | 生成器内置 LaTeX 符号映射：Σ∏×·÷≤≥≠≈±∞∂∀∃∫→←⇒ 与希腊字母全集——写公式直接用 `\sum` `\times` `\leq` `\alpha` 等标准命令即可，无需人工改写为 Unicode 字符 |

## 3. 生成管线（md → docx）

```
交底书 md（mermaid 围栏源码 ＋ 紧随其后的图片行）
  → 附图 PNG：黑白线图规范（见下），存案件文件夹
  → node 〈skill〉/scripts/docx生成/generate.js 〈输入.md〉 [-o 输出.docx] [-i 附图目录]
  → postcheck（documents:docx skill 的 scripts/postcheck.py，全项通过）
  → 渲染页视觉抽查（PDF/页图抽查关键页：图页、公式页、表格页）
  → 双读核验（写后回读，防间歇性写失败）
```

**md 图片行约定**（generate.js 的插图驱动）：`![图N　图题](文件名.png|宽=560)`——alt 文本＝图题（原样进 docx），目标内 `|宽=NNN` 为显示宽度（磅，可省略用默认）；文件名相对附图目录。mermaid 围栏本身不落 docx（保源码供编辑），渲染 PNG 由图片行引用。

**附图规范**（黑白线图）：矩形/菱形/箭头完整闭合、无裁切半边、箭头不穿框；**图元之间贴近但不得重叠**（每个矩形/圆角矩形的边界完整可见）；**图内不出现图名**（图名只在图题）；节点标签含步骤号；单图宽度控制避免整页空白（宽度过大→占页溢出，参照已验证值：横幅框图≈560、纵向流程≈430）。

**附图视觉核图（多模态）**：附图页渲染后，派宿主多模态能力（如经 ai-cross 派发视觉模型）对每张图核对——元素是否重叠/裁切、图名是否入图、框线是否闭合、图题与图内容是否对应；命中问题修图重嵌，核图结论留痕（可与渲染页抽查记录同文件）。

**失败处置**：OMML 转换失败的公式保留 LaTeX 原文并在问题清单记录（不得退回图片公式）；Node 环境缺失时交付 md＋说明，不得改用无模板 pandoc 顶替。
**加固红线**：输出 docx 一律由 generate.js 一次生成——**禁止用 python-docx 等工具重存输出件改格式**（重存会改变 zip/XML 序列化特征）；需要新的排版加固（如某类段落防孤行）时，把需求提到 skill 层修改 generate.js 并登记本文件，不得在案件侧临时后处理。

## 4. 红字两阶段（过程稿 → 定稿）

| 阶段 | 做法 |
|---|---|
| 过程稿（供用户复核） | 四类内容红字：①`## 注意事项` 整节（给书写者/代理看的话）；②任意位置的`【待确认：…】`占位；③`【提示：…】`书写者提醒（模板占位提示、过程性说明等）；④附图说明/参考文献节条目尾部说明性括号 |
| 用户确认 | 用户人工复核后明确说"红字可删"（或逐条确认） |
| 定稿 | 删除全部红字内容 → 重新生成 docx → **定稿红字清零为验收项**（self-check §6） |

红字是给书写者的过程标记，**永不进入正式提交件**。

## 5. Word 修订应用（用户批注/修订 → md 新版本）

用户在 docx 中用修订/批注反馈时：
1. 解析 `word/comments.xml`（批注）＋ `word/document.xml` 中 `w:ins`/`w:del`（修订）；
2. **必须全量扫描：正文段落＋表格单元格内**（曾发生漏扫表格内修订致用户修订丢失——教训：段落与表格逐节点全量遍历）；
3. 应用到 md 生成新版本（字符串替换须带失配检查，失配即停并报告，不得静默跳过）；**用户已确认的修订在新版本中必须保留**；
4. 重新生成 docx → postcheck → 回读核对修订点已落实。
